# Performance baseline 0.3.0 (DEV-031)

Baseline for NFR-003: TC-142 (startup) and the TC-143 frame-timing baseline, measured with `:benchmark` against the app's
`benchmarkRelease` build. **These are emulator numbers, so they show a trend only (testing-plan §1.3).** The authoritative
run is on the iMin device. It is pending until a unit is available, and at 0.8.0 at the latest (TC-142–TC-144).

## Setup

| Item | Value |
|---|---|
| Date | 2026-10-24 |
| Device | Emulator `Pixel_10` AVD (`sdk_gphone64_arm64`, API 37, 1080 × 2424, 420 dpi), headless (`-no-window`), host GPU emulation (`skiagl`), on the developer Mac |
| App build | `benchmarkRelease`: R8 and resource shrinking as in release, not debuggable, profileable, signed with the debug key. The backend, serial number and connectivity are the `:core:testing` fakes (happy path) through `BindingOverrides`, so the kiosk signs in and binds "Urban Grill" offline. |
| App state | Bound to Urban Grill (the setup step signs in and binds once per install) |
| Screens | Splash, Sign in and Choose a restaurant are the 0.2.0 screens. **Idle, Order type, Menu and Item detail were still the DEV-010a placeholders**, so the journey numbers measure the navigation skeleton, not the 0.3.0 screens. |
| Baseline profile | Generated by `BaselineProfileGenerator` on the same emulator (`nonMinifiedRelease`), 24 977 rules, committed in `app/src/main/generated/baselineProfiles/`. The release APK ships it as `assets/dexopt/baseline.prof` (TR-PRF-19). |
| Benchmark library | Macrobenchmark 1.5.0, `androidx.benchmark.suppressErrors=EMULATOR` |

## TC-142: cold start (TR-PRF-01, target ≤ 1.0 s median on the device)

`StartupBenchmark`, `StartupTimingMetric`, `StartupMode.COLD`, 10 iterations each. The first frame is the Compose
Splash (SCR-01); the 3.9 s minimum splash time (TR-PRF-02) is not part of this metric.

| Test | Compilation | timeToInitialDisplay min | median | max |
|---|---|---|---|---|
| `coldStartWithoutProfile` | `None` | 573 ms | **900 ms** | 1 552 ms |
| `coldStartWithBaselineProfile` | `Partial` (baseline profile) | 587 ms | **711 ms** | 828 ms |

Before the profile was generated, the same two runs gave a median of 681 ms (`None`) and 806 ms (`Partial`, no profile
yet), which shows the emulator's run-to-run spread of about ±150 ms. With the profile, the median is within the 1.0 s
target and the maximum is 828 ms instead of 1.5 s.

## TC-143 baseline: J1 browse frame timing (TR-PRF-05, target P90 ≤ 16 ms and ≤ 1 % janky frames on the device)

`JourneyBenchmark.idleToItem`, `FrameTimingMetric`, `CompilationMode.Partial`, 5 iterations. Each iteration starts a
fresh process on Idle (not measured), then measures Idle → Order type → Menu → (category) → item → back to Menu. On the
placeholders, the category step is skipped and the steps are "Tap anywhere", "Pick an order type", "Product card" and
"Keep ordering".

| Metric | P50 | P90 | P95 | P99 |
|---|---|---|---|---|
| `frameDurationCpuMs` | 63.0 | 91.0 | 101.4 | 143.6 |
| `frameOverrunMs` | 68.1 | 110.6 | 123.8 | 156.4 |

`frameCount` per iteration: min 75, median 96, max 100.

These numbers are not usable against the target. The headless emulator renders through host GPU emulation, and the
placeholders are not the screens 0.3.0 ships. Re-run `JourneyBenchmark` once the 0.3.0 screens are merged, on an emulator
with a window as a trend check, then on the iMin device. The 0.3.0 exit criterion asks for a tracked issue for any screen
above 16 ms P90 on the emulator. Raise those issues from the re-run on the real screens, not from this table.

## JankStats (debug and `benchmarkRelease`)

`JankStatsFrameDiagnostics` logs each janky frame as `frame_jank duration_ms=… states=…` (DEBUG) and a summary as
`frame_summary frames=… janky=… janky_percent=…` (INFO) when the Activity pauses. A debug build cold start, Splash →
Idle, then Home logged `frame_summary frames=77 janky=0 janky_percent=0.0`. In `benchmarkRelease`, no Timber tree is
planted until DEV-073 adds the rotating file log, so the summaries are not visible there yet. `FrameTimingMetric` is the
measurement there.

## How to re-run

```bash
# Emulator or device connected; the test APK installs benchmarkRelease itself.
./gradlew :benchmark:connectedBenchmarkReleaseAndroidTest \
  -Pandroid.testInstrumentationRunnerArguments.class=com.hitachi.kiosk.benchmark.StartupBenchmark
./gradlew :benchmark:connectedBenchmarkReleaseAndroidTest \
  -Pandroid.testInstrumentationRunnerArguments.class=com.hitachi.kiosk.benchmark.JourneyBenchmark
# Regenerate the baseline profile (commit app/src/main/generated/baselineProfiles/ afterwards).
./gradlew :app:generateBaselineProfile
```

Results are written to `benchmark/build/outputs/connected_android_test_additional_output/benchmarkRelease/connected/<device>/`.
On the iMin device, remove `androidx.benchmark.suppressErrors=EMULATOR` from `benchmark/build.gradle.kts` so that
Macrobenchmark's configuration checks apply.
